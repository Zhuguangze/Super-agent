# 0005 - 并发会话:单 WS 连接多路复用

一个 User 的多个 Session 的 Run 可以**并行执行**：运行中切换会话、新建会话不再被拦截，原会话的回复继续生成并落盘。实现上选择**单条 WS 连接多路复用**——所有会话的事件走同一条连接，后端给每个下行事件补 `session_id`，前端状态仓按会话分桶（messages/running/排队数/审批/未读全部按 session_id 路由）。运行注册表从 `user_id → RunHandle` 改为 `(user_id, session_id) → RunHandle`。

## Considered Options

- 每会话独立 WS 连接——被否：事件天然隔离但连接的鉴权/重连/生命周期管理×N，前端 connection store 与 App 装配全改；会话数通常个位数，隔离收益不抵复杂度
- 单连接多路复用（采纳）：改动集中在"事件补 session_id + 前端按会话分桶"，贴合 spec §4.2 的单通道设计

## Consequences

- 所有下行事件（相位/工具/错误/审批/队列）必须携带 session_id，新事件类型一律遵守
- 并发 run 共享同一 Workspace：同用户多会话同时执行 bash/文件工具可能互相踩文件（内网单用户场景接受）
- 运行中删除会话：后端先定点 cancel 该会话的 run 再删除，防止向已删 JSONL 写入
- 目标会话运行中拒绝 Branch 与 Compact（与活动 run 的写入竞态不做 v1 处理）
- 刷新落在 run 中途：重连回放只到最近落盘处，进行中的轮次等 message_end 补齐（已知瑕疵）
- 前端消息/运行态按会话分桶后，无会话态（hero 首发未回 id）回落 `__pending__` 临时桶
- **重审触发条件**：当单会话的事件量级（如未来多 Agent 可视化工作流、实时推荐结果流）饱和到影响其他会话事件的实时性时，按**事件类别**（而非按会话）拆分通道；多 Agent 场景的新事件届时携带 agent_id，前端"按会话分桶"的路由模式不变。配套缓解已落地：流式 delta 按 ~100ms 合帧批量应用（降低高频 token 事件的主线程占用），回放采用会话桶缓存（看过的会话切回即用本地缓冲，不重拉）
